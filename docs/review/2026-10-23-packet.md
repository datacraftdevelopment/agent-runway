## Plugin contract draft

# Runway Agent plugin: what the skills should be

Proposal, 2026-10-23. Nothing built. Pairs with pm-sp; works without it.

## The short version

One plugin, **`runway-agent`**, that lives in the runway-agent repo beside the app and is also listed in the dc-dev-plugins marketplace (sourced from that repo, the way fm-lens is). Five skills, one hook, and a small CLI that owns every rule. The skills are prose for the model; the CLI is code, so the merge rule and ticket states are written once and can't drift (v1's lesson: keep every rule once, in one protocol).

For Monday, build only the loop: `file-tickets`, `work-ticket`, `review-ticket` and the CLI's gate, run on one practice-repo ticket end to end. `setup`, the session hook and `board` come after that has run for real.

## Where it lives (recommendation)

**In the runway-agent repo, under `plugin/`, and listed in dc-dev-plugins' marketplace.json with a GitHub source.**

- The plugin is the contract the app reads (ticket file format, receipt kinds, gate). Keeping it in the same repo means one version of the contract, one PR when it changes, and a stranger installs the app and its skills from one place.
- dc-dev-plugins is written for Joe's machines (pm assumes Ringer). Runway Agent must not.
- Listing it in dc-dev-plugins keeps Joe's rule of one marketplace per machine: Joe installs `runway-agent@dc-dev-plugins`; strangers add the runway-agent repo as their marketplace.
- Name: `runway-agent`, not `runway`, so it never collides with pm's old `runway` skill.

## The skills

### 1. `file-tickets` (end of shaping)

Turns finished shaping into tickets. Reads a pm-sp plan (`docs/plans/…`) and its design doc, or a wayfinder map's destination chunks, and cuts them into tickets.

- **One ticket = one branch = one PR**, sized for one unattended session. The plan's tasks stay inside the ticket as commits; a ticket points at its plan, it never restates it. (This keeps pm-sp's rule that build work lives in designs and plans: the ticket is only the run order around them.)
- Each ticket file carries: title, repo, spec and plan paths, the Acceptance lines it must satisfy, `Risk:` (default `not-low`; `low` only with a one-line reason), `Touches:` (expected paths), `Blocked by:`, and `Model:` if it matters.
- Shows Joe the batch as a short table first and files on his go. Joe's go is the only go.
- Without pm-sp it accepts any spec file with an Acceptance section, so Matt's `/to-spec` or a hand-written spec works too.

### 2. `work-ticket` (the worker)

What a session started on a worker machine (or in the cloud) runs. Workers run inside a Herdr pane (`HERDR_ENV=1`), started by the controller with `herdr --machine <label>`; Herdr reports agent state (idle, working, blocked, done), and the receipts add the why.

- Claims through the CLI (`claimed` receipt) before touching anything; a second claimer loses.
- Fresh worktree on a `runway/<ticket>` branch, reads the repo's `docs/agents/worker-env.md` and the spec.
- Builds with pm-sp's `subagent-driven-development` when it's installed, else inline TDD. Decisions the plan didn't settle get made and written down as rulings in the PR body, as pm-sp does.
- Runs the repo's check command fresh and pastes its output into the receipt.
- Opens a draft PR that says "Refs", never "Closes". Never merges.
- Ends with exactly one closing receipt: `done`, `blocked` (a dependency), `needs-you` (one question, with a recommended answer), or `failed` (with the output). Irreversible, security or outside-the-worktree steps always stop as `needs-you`.

### 3. `review-ticket` (second model)

A reviewer on a different model from the builder (Codex if Claude built it, Claude if Codex did), pinned to the exact commit it reviewed.

- Reads the diff against the spec's Acceptance lines and the repo's `REVIEW.md` if there is one.
- Verdict: `pass`, `fix` (findings go back to the worker for one fix pass) or `needs-you`.
- May raise risk to `not-low`, never lower it. The CLI enforces that, not the reviewer.
- Ringer is optional: if `ringer` is on PATH it dispatches through it, otherwise it calls `codex exec` or `claude -p` directly.

### 4. `setup` (first run, for a stranger's machines)

The wizard's steps, written so Claude can walk someone through them or the app can run them.

- Controller: where tickets and receipts live (`~/.runway-agent/`), nothing hardcoded.
- Each worker: Tailscale SSH reachable, `claude` and `codex` signed in **inside a non-interactive SSH session** (the keychain risk, tested first), a Herdr server running, plugin installed.
- Each repo: `runway.json` (check command, sensitive paths, default risk, which machines may take it) and `docs/agents/worker-env.md` from a template.
- Reports a green/red table; fixes only what the person approves.

### 5. `board` (from inside any Claude session)

Read the board and answer it without opening the app: what's running where, what needs you, the last receipt per ticket. Answering a `needs-you` card from here writes the same answer the app would. Pause/resume dispatch for a repo or machine.

### Hook: `session-report`

SessionStart and Stop hooks (plus a status ping on each turn end, rate-limited) so every session, including hand-started steered ones, shows on the board: machine, repo, branch, kind (`steered` or `ticket`), state. It only reports; it never injects instructions into the session (the takeover pm-sp removed from Superpowers).

## The CLI underneath (`runway-agent`, Python, stdlib only)

The skills call it; the app reads what it writes.

- `ticket new|list|show`: the ticket files.
- `claim`, `receipt <kind>`: append-only receipts, one JSON line each, with machine, session, commit and time.
- `gate <ticket>`: the merge rule as code. Auto-merge only when risk is `low`, review passed on the head commit, checks are green, and no changed path matches the repo's sensitive list (auth, payments, migrations, CI by default). Anything else becomes a `needs-you` card.

2. **Cloud sessions' receipts.** They can't be reached over SSH. Simplest: they push their branch and the controller reads receipts from the PR. Needs a check with the app thread.
3. **Where it lives.** runway-agent repo plus a dc-dev-plugins listing (recommended), or a plain subfolder of dc-dev-plugins.
